# Backbone review: structured results

## review-extend.md

**Headline.** The plan's science rules hold, but it names almost no interfaces; fix about ten record shapes and id rules now (own object key, claim record, source registry, three versions, forecast register, self-describing data set), refuse every framework around them, and build a no-model skeleton over the two snapshots on disk before the stack conversation.

Report written to docs/research/architecture/review-extend.md. Nothing in it chooses a framework, server language or host.

The plan fixes a few rules (one network module, a licence class per source, three cell states, an alias table) and leaves open what an adapter returns, what a ledger record holds, how records become a displayed row, what a forecast record is, and what the app receives. Each of the eight future changes is cheap or expensive depending on those shapes, and an agent would invent each while building a feature.

Three things are wrong as written.

1. Identity. The plan keys on "JPL's permanent id". Neither snapshot contains it: the SBDB pull did not request `spkid` and the reachable list has only the designation. JPL's lookup documentation (read today) shows Apophis with primary SPK-ID 20099942 and aliases 3264226 and 2099942, so the id is not stable across numbering. Confirmation-page candidates have no JPL id at all; of 1,381 that left the MPC page since 1 August, 737 received or matched a designation and 644 did not (fetched today). Fix: the project mints its own opaque key, with dated aliases, a lifecycle field, and merge and withdrawal records.

2. The cell key (object, property, source) cannot hold two values from one source. Fixture object 2009 BD has two size solutions from one paper, and SsODNet marks its 2009 BD reflectivity "Computed". Fix: a claim record with its own id, closed lists of value kinds and states, a property registry, and one function from claims to a row.

3. "Pulls only what changed." JPL's responses have no ETag or Last-Modified. The reachable list came back with fields in a different order (0 of 7,229 records byte-identical, 7,007 after sorting). Of 222 changed records, 192 changed only in window fields on an unchanged orbit; for 187 the window start moved from 21 to 27 November, across the full moon. That leaves 30 real changes in 3.4 days. The two JPL lists also disagree within one pull (H for 327 objects). SBDB offers `soln_date`, not requested so far.

By item:
- Sources: the coverage check used about 25 static tables and three services, so a table source should be a mapping file and an adapter should only turn a stored response into claims. A release is part of a source's identity; retiring is a dated status change; the project's own analyses (colours from Rubin photometry, orbit refits) enter as sources beside JPL's values.
- Properties and derived quantities: registry entries; derived quantities as functions of the joint model's draws plus one configuration entry.
- Widening: hold all 43,379 near-Earth objects from day one (same single request) and make "reachable" a named population. JPL's list is a parameterised query whose default launch range, 2020–2045, includes past years and was changed once before. Per-object pulls for all objects are 12 hours at one a second; SsODNet's several-object route works (tested with three; an unknown object returns an `error` entry inside a 200).
- Method changes: three version numbers (schema, method, data); a forecast register and a resolution log that are only added to; scores as a function of those two. Old predictions stay scorable because they are stored, not because old code runs. Claims need published and first-seen dates (SsODNet records are 71 days old).
- Visitor state: public stable ids for objects, questions, presets and forecasts; nothing a visitor enters flows into the pipeline.
- Other users: one licence filter producing a page view and an open view; inputs recorded per object and per method; reported measurements as a reviewed source; a DOI per method release, not per refresh.
- The DESIGN.md contract rule holds against items 2, 4 and 5 with five additions: registries inside the data set; an explicit list of what the app may and may not compute (no summing probabilities over a visitor's filter; every offered filter combination is an exported preset); versions on every derived value with forecasts in their own tables; one scoring exception if visitors ever predict; a stated meaning for clock-dependent fields. Plus a conformance kit.
- Agents: stages with schemas, a contract test per source on stored responses, invariants, two kinds of golden file, a lock file on frozen inputs, an import check.

Six interfaces should exist before any feature: identity, sources, claims and rows, versions, forecasts, the data set.

First step: owner decisions (key, versions, state list, JPL contact address, because history cannot be backfilled and daily capture is 3.3 MB gzipped per pull); the contract as a short document; a skeleton over the two snapshot dates on disk for all 43,379 objects with no model, app or network, including the change list; then one static table and the 1,704 SsODNet records from the archive; then the stack conversation with a real data set in hand.

Limits: no JPL interface was called (four documentation pages read); cost statements are my judgement of what must be touched, not measured effort; the full-moon cause is inferred; Rubin facts and the Gaia archive closure are from the 21 November check.

## review-ops.md

**Headline.** Start collecting daily now and get the project off one disk: the data is tiny, but each day's upstream state exists once, nothing is backed up, and the workstation is only on 70% of the time.

I reviewed the plan as the sole maintainer for five years, using the two local JPL snapshots, the workstation's own logs, and prices and limits read today. No JPL API call was made. The report chooses no app stack.

The operating problem is small in money and data and large in one respect: history. Two bulk requests a day capture everything fast-moving. Kept whole and compressed, that is 2.57 MB a day and about 4.7 GB in five years, inside the free allowance of either object store I priced. JPL's lists show only the current state, and the prediction record depends on proving what was known on a date, so collecting is the only work where delay loses something permanently.

Three findings change the plan:

- Nothing is backed up. The repository has no remote, no scheduled backup is configured, and the docs, the 570 MB evidence archive and both snapshots sit on one NVMe drive. A backup made some other way would not have shown in the places I looked.
- The workstation is not "always on". Over 41 days it was powered about 70% of the time. The plan's weekly refresh on this machine would fail silently.
- Weekly is the wrong cadence, and a naive diff is the wrong signal. JPL recomputes the reachable list daily, and its window fields are relative to the day it ran: 171 of the 222 changed rows changed only in window start or brightness. A table three days old had 11% of its "open now" windows wrong, and ten days old 17%, so the plan's idea of working out "open now" in the page from stored dates does not hold. JPL also shuffles key order between pulls, so a raw-file hash can never say "unchanged", and the responses carry no data date or cache headers, so "pull only what changed" is impossible for the bulk lists.

Where scheduled work can run: the workstation ($0, off 30% of the time), a code host's scheduled job ($0; GitHub documents dropped runs under load and switches schedules off after 60 quiet days in public repositories), a small server ($4–7 a month, plus patching), or a managed platform ($1–5 a month, needs a bucket). None is reliable alone, and the job is cheap enough for two triggers, the second pulling only if today's snapshot is missing. The 5 GB orbit fitter stays on the workstation, in its own environment, so it can never break the daily loop.

Serving: a public service's duties come from the write path and from personal data. A read-only service over a versioned data set has almost none: nothing to back up, and releases are atomic swaps. A small anonymous write path adds backups and rate limits. Accounts add everything else. Safari deletes script-writable storage after seven days without interaction, so browser storage cannot hold a prediction that resolves in 2027–2030. "Not hosting static data" can mean self-refreshing data or pages made on request from a database, both cheap; it cannot mean holding no upstream copy.

Monitoring: a dead-man's switch on the store, one weekly digest built from a parsed diff, a stale banner computed at viewing time, and holds that never clear themselves. Non-null counts of physical fields were identical across the two pulls, so any fall is a sharp fault signal.

Recommended shape:

- **First three months:** a daily collector into a locked private bucket mirrored to the workstation, a private remote, the switch and the digest; no server and no site. $0–1 a month, about a day to build, then five minutes a week (my estimate).
- **Year two:** the same collector, self-promoting guarded data refreshes, hand-run method releases, and the lowest serving shape that satisfies the decision on visitors' predictions. About $15–110 a year. Attention is my estimate: 10–15 minutes a week, about two hours a month once ten adapters exist, and half a day a quarter for a replay-and-restore drill.

First step, in order: get the project off one disk; decide the JPL contact address, which unblocks all automation; then build the collector and its store and switch it on. It can be written and tested offline today from the two snapshots, and it runs in parallel with the fixture slice and the stack conversation.

Limits: change rates rest on one 3.4-day interval, and the full-moon explanation of the window gap is an inference.

### Findings

- **Backups**: Nothing in the project is backed up. - **Where scheduled work runs: workstation**: The workstation is not always on. 23 boots in 41.4 days, powered 70% of the time, 15 gaps over an hour, longest 6.3 days; no uptime at all on 7-11 November; powered at 03:00 on only 23 of 42 days; off overnight on 9 of the last 12 nights. Neither response has an ETag, Last-Modified or a data date. NHATS returns count as a string, SBDB as an integer. JPL documents HTTP 200 responses that carry an error message. Consequence: "Pull only what changed" is impossible for the bulk lists: always pull both whole, then parse, sort keys and compare. Store raw bytes by date and source, not content-addressed. The as-of date is the pull time. Validate status, parse, absence of an error key, signature.version, field list, count and canaries before calling a snapshot good. (My test today on data/snapshots/2026-11-21 and /2026-11-24 (script in the report appendix); saved headers in data/snapshots/2026-11-24/*.headers; https://ssd-api.jpl.nasa.gov/doc/nhats.html read today.)
- **Observing windows go stale fast**: Window start and window brightness are relative to the day JPL computed the table. 171 of the 222 changed reachable rows changed only in those two fields. On 21 Nov 212 windows started 2026-11-21; on 24 Nov none was open and 206 started 2026-11-27. Of the 212 open on 21 Nov, 2 had closed after 1 day, 24 (11%) after 3, 36 (17%) after 10, 90 (42%) after 30. For 110 objects with the same window end the listed peak faded by a median 0.25 mag, up to 1.52. Consequence: Pull daily, not weekly. Do not compute "open now" in the page from stored dates (plan 5.3); show windows as dated facts with the table's as-of date and say "open now" only when the table is under two days old. Replace the single ten-day banner with a freshness budget per source. Build the weekly digest on a parsed diff that filters out re-dating, or it reports about 220 changes every few days. (My test today on the two snapshots. JPL's API page does not define obs_start, obs_end or obs_mag (https://ssd-api.jpl.nasa.gov/doc/nhats.html, read today). The full-moon explanation is an inference from JPL's observability rules (research of 21 Nov, https://cneos.jpl.nasa.gov/nhats/obs.html, not re-read).)
- **Daily cadence matches upstream**: CNEOS describes NHATS as the result of a daily automatic analysis. ## review-data.md

**Headline.** The plan is sound on what to compute but was written around one frozen pull. Fix three things in the schema now (our own object key, a stored record of having looked, separate stamps for data and method), start archiving daily, and the site can be current while the science stays frozen.

I reviewed AGENTS.md, DESIGN.md and docs/plan.md (Appendix B and C line by line) against the two local JPL pulls, five JPL documentation pages, four Minor Planet Center pages and one test request each to SsODNet and the Minor Planet Center. No JPL API call was made.

WHAT BREAKS UNDER DAILY DATA
- Identity. The plan keys everything on "JPL's permanent id". That id (spkid) is not among the 53 fields in either pull, and JPL's own documentation shows it changing: Thetis has a "historical alternate SPK ID" and Apophis lists a retired id among its aliases. SsODNet's id is a name. Addresses, seeds and sealed lists would hang off a key that moves at numbering.
- "Not checked" has no record. Nothing stores the act of looking, so a missing value cannot be told from a failed request.
- One version axis. A "release" bundles data, method and site, and "nothing with a model in it runs in the weekly loop" would leave new objects without a prior.
- The release guard assumes a person promoting a batch and simple tolerances. Normal churn already includes 222 of 7,229 rows changing in 3.4 days.
- Observing windows. 85% of changed values on the reachable list are window and radar-opportunity fields moving with the calendar. The window start is clamped to JPL's computation day and skipped past the 24 November full moon (187 objects moved from 21 to 27 November). Twelve open windows vanished in 3.4 days, because only the next window is listed. "Open now from stored dates" (plan 5.3) is wrong.
- Counts are not constants. One object moved from 7.274 to 6.820 km/s on a new orbit, so the plan's 1,388 is already 1,389. Two of the ten fixtures changed upstream in 3.4 days.
- A silent format change is in progress: orbit solution numbers appear as "49" and "JPL 49", and 20 objects flipped form between pulls. JPL's API version strings have not changed since 2019 and 2021.

VERSIONING
Three clocks. A data state is a batch number plus a chained hash over every accepted batch; because values are never rewritten, "the data as of batch N" is a query, not a copy. A method version is a git tag holding priors, thresholds, presets, the unit registry and the price scenario, deposited at a gate. The export schema is versioned separately. Every derived value is keyed by object, property, method version and a hash of its inputs. Applying a frozen method is a pure function and runs on every change; tuning one never runs unattended. A number shown today is reproduced by checking out the method tag, querying the store as of the stated batch, and comparing export hashes.

STORAGE
Recommended: content-addressed raw responses underneath, an append-only table of statements by source on top, and a rebuilt current view for the app. Raw alone answers no question; statements alone cannot be repaired after a misreading. Size is not a constraint: 108,400 filled values on the reachable list, 1.29 million in the full near-Earth table, about 800 changed values a day. A full copy of both lists daily is 1.2 GB a year gzipped; changed rows alone are about 4 MB a year. The report gives the DDL for fetch, batch, object, designation, source_row, statement, coverage, membership, derived and forecast tables. SQLite is proposed for the pipeline's working store only and needs the owner's yes. Nothing chooses the app's stack; section 4.6 lists what that choice turns on.

DAY-ONE SCHEMA
Our own key for all 43,379 near-Earth objects with every upstream name as a dated alias; values kept as received ("10.", "0.00") beside the parsed value; signed bounds with a kind, a limit flag and a qualifier; the original reference stored so two routes to one paper are not counted as agreement; no rule that a cell has one value; upstream errors annotated, never edited.

DRIFT
Fifteen guards run before a batch is accepted, with a held batch archived and the last good data served per source. Tests: the two existing pulls as golden fixtures, thirteen single-fault mutations each asserting that no cell becomes "looked for and absent", a rebuild-from-raw replay, and a restore test.

### Findings

(Own test on data/snapshots (appendix script, line 1). https://ssd-api.jpl.nasa.gov/doc/horizons_lookup.html and https://ssd-api.jpl.nasa.gov/doc/sbdb_query.html, both read today via summarising fetch.)

Rows are never deleted. - **Ledger states**: The plan defines measured, looked for and absent, and not checked per cell, but stores no record of the act of checking. The first of the two existing pulls has no header file, so its retrieval time survives only as a file timestamp, and the folder named 2026-11-24 holds a pull made on 2026-11-25 UTC. Consequence: A fetch row for every request, successful or not, and a coverage table separate from values. A failed request writes a fetch row and nothing else, so no cell can move to "absent" because of an outage. All times in UTC. (docs/plan.md Appendix B (Ledger cells, Network); data/snapshots/2026-11-24/nhats.headers (Date: Wed, 25 Nov 2026 01:12:45 GMT); file timestamps read today.)

The earliest window start was 2026-11-21 in the first pull and 2026-11-27 in the second; 187 objects moved from one to the other across the 24 November full moon. Twelve objects with an open window on 21 November had none three days later. The peak brightness got fainter for 112 of the rolled rows and brighter for none. Consequence: Mark window fields as clock-driven and exclude them from "what changed". Do not derive "open now" from a stored start date (plan 5.3). Keep closed windows in history, because upstream drops them and the record needs them. (Own test (script lines 8 and 9). Consequence: The diff of the bulk table is the change feed that triggers per-object pulls. Each value's date is its solution number, not the pull date. ## upstream-orbits.md

**Headline.** The fast-moving data can be kept current with two JPL requests a day plus about ten per-object calls; no live or push access exists or is needed, and the only thing that cannot be recovered later is history, so the daily archive should start first.

Scope: what dynamic access exists to orbits, tracking and observing windows, and the cheapest correct daily sync. Method: re-diffed the two local JPL snapshots (16:35 UT 21 Nov and 01:12 UT 25 Nov), read JPL, Minor Planet Center (MPC) and ESA documentation today, and made about 24 single requests to MPC, ESA and NASA NeoWs. No request went to a JPL API endpoint.

Main conclusion. Every source refreshes about once a day, all driven by one event: the MPC's Daily Orbit Update circular, issued around 12:30 UT. JPL has no "changed since" filter, no cache headers and no push channel, and its terms forbid calling it from a website. So "dynamic" means a scheduled daily job writing to the project's own store. Two bulk requests (reachable list 2.6 MB, near-Earth table 15.8 MB) cover list-level data for all 43,379 near-Earth objects. A typical day for the reachable list is 11 to 24 requests and about 21 MB; adding a single-object call for every changed near-Earth object makes it 105 to 160 requests.

What the tests showed.
- All 342 changed near-Earth rows have a new orbit_id, so it is a complete change key. The last-observation date misses 126 of them.
- JPL responses cannot be hashed as bytes: key order differs between pulls.
- 204 of the 216 changed window starts are one rolling edit (2026-11-21 became 2026-11-27 on every open window). Ignoring window start and brightness, 51 reachable rows changed, not 222.
- The reachable list lags the orbit table: all 14 reachable objects in the 24 Nov circular had a new orbit in the table 12.7 hours later and the old one in the reachable list. Two objects were behind at both pulls.
- The 24 Nov circular lists new observations for 184 objects; 182 had a new JPL orbit by the second pull and 2 were new to JPL.
- ESA's updated_nea.lst is a timestamped change log back to 5 June 2026 with removals. It contains 338 of the 338 asteroid orbit changes JPL made between the pulls and nothing JPL did not change. Over 91 days it shows a median of 152 objects refitted a day (90th percentile 255, maximum 462), so the 102 a day in the brief is a quiet stretch. On 30 July 2026 ESA refitted 46,027 entries in one day.
- 2026 JG2 is on JPL's reachable list today, but the MPC's identifier service does not know it and ESA logged its removal on 5 June. A vanished JPL row can mean merged, reclassified or withdrawn; only the MPC identifier service (100 ids per request) says which.
- The MPC and ESA each publish their own fits with a sunlight-push term and covariance (checked on 2022 OB5), so there are three sources for those values. ESA's terms allow personal non-commercial use and no redistribution without written permission.

What the documentation says. The JPL bulk query documents fields the snapshots did not request (spkid, soln_date, source, full precision). It cannot return the force law, covariance, physical-parameter references or alternate ids; the single-object call does. No JPL interface version relevant here has changed since March 2023. The MPC API limit is 5 requests a second, one designation per observation request; its bulk observation files are seven months stale; the replicated database needs 4 TB and an always-on server under an internal-use licence. Horizons is one target per request and saved ephemerides ran to 220 kB each, so recomputing windows across the list is not sensible.

What cannot be automated: physical measurements, the true start of an already-open window, yesterday's orbit once JPL replaces it, a whole-catalogue refit day, an unannounced format change, and the rule for withdrawn objects.

Not verified: any live JPL behaviour (full precision on push values, compression, single-object size with covariance, when the trajectory batch finishes, whether an SPK-ID changes at numbering), and when JPL's User-Agent rule appeared.

## upstream-physical.md

**Headline.** Physical measurements have no change feed anywhere. Orbits and tracking can be shown as current; every size, spin and class can only be dated, and every "not measured" is only as good as the oldest source behind it (SsODNet is 71 days stale today, and one live table it lacks adds 7 rotation periods under 6 km/s).

Scope: where new physical measurements of near-Earth asteroids appear, how fast, and what machine signal each source gives. All checks ran 2026-11-24; no JPL API call was made.

What I found:

1. No upstream offers a change list for physical data. The signals that exist are file dates (Last-Modified/ETag) on about ten static files, a build stamp inside each SsODNet card, an export date on each row of one observer's table, and the daily arXiv listing. Everything else is pull-and-compare.

2. A measurement appears first in the observer's own table or paper, reaches SsODNet months later in irregular batches, and mostly never reaches JPL's database (0 physical-field changes in 3.4 days).

3. SsODNet has not rebuilt since 14 September 2026. All 13 cards that answered today carry that stamp; its bulk table, reference list and name index are dated 22 September; its name index knew none of three later designations. Its 2023 paper says weekly for names and plans monthly for the rest. At least 144 of the 7,231 reachable asteroids were first observed after the stamp, so SsODNet returns 404 for them. It has no change list, version endpoint or archive of old builds. Its reference list (4.5 MB JSON) can be diffed to see which papers a rebuild added. The bulk table accepts range requests and ran at 18 to 147 kB/s today.

4. A live source the project does not use changes its counts. Pravec's Ondrejov results file (one fixed-width text file with file dates and a per-row export date) holds periods for 35 reachable asteroids missing from the project's 21 November union of JPL, the lightcurve database and 1,704 SsODNet cards. Twenty are confirmed absent from SsODNet; 15 never had a card fetched. Seven are under 6 km/s and four under 5 km/s, all confirmed today (44 becomes 51, 20 becomes 24). 2023 RA4 (4.96 km/s) has a 2.35-hour period at grade U 2, which contradicts the plan's sentence that every measured period under 5 km/s is faster than 2.2 hours. 1999 AO10 (5.89 km/s) has had a secure 11-hour period in public since March 2026.

5. The lightcurve database (LCDB) is frozen at 1 October 2023, yet the largest recent survey of small-asteroid spins names it as its data route. ALCDEF (raw photometry) is live and searchable per object by web form, with research-only terms; its bulk file is 19 months old and its "added since" export returned HTTP 500. The Minor Planet Bulletin is quarterly PDF, indexed by ADS; SsODNet's Bulletin coverage has a hole for 2022 to 2024 and none of 2026.

6. Today's arXiv listing has a characterization paper for 2026 QQ8, a fixture object and the lowest delta-v object on the whole list. Its abstract contains none of "near-Earth", "NEA", "NEO". Only designation matching finds it, and titles typeset designations with TeX subscripts ("2026 QQ$_8$"), which a plain pattern truncates.

7. Minor Planet Center records are live to the hour and carry magnitudes and bands, but not simultaneous colours, a common photometric system, record timestamps or a "since" query. They support a "photometry exists" flag, not a displayed class. Rubin's camera has been off since 15 November.

8. Sizes are the slowest channel: NEOWISE and Spitzer are static, NEO Surveyor is unlaunched, radar results appear only in papers.

9. Strasbourg's VizieR is degraded by a declared cybersecurity incident; its Harvard mirror returned HTTP 200 with a database error as the body. TAP and new-table detection could not be tested.

10. Prices: the only licensable machine-readable source covering all five metals is the USGS yearly data release (CC0, CSV). Johnson Matthey forbids any use without consent; LBMA prices need a licence. Capability facts have no machine source.

Classification (section 9 of the report): automatic daily for the reachable list, orbit quality, tracking, radar-exists and Minor Planet Center records; automatic detection but source-dated values for SsODNet and Pravec; scheduled reviewed checks for the literature watch, the Bulletin, MITHNEOS spectra, yearly prices and prediction resolution; hand-curated with "last checked" for one-time paper tables, Gaia DR4, mission watch items, dealer prices, capability facts and method thresholds.

What the site may claim: "current" for list membership, delta-v, observing windows and tracking, labelled with JPL's solution and the last successful pull. "Source build date plus checked date" for every measured physical value. Only "last checked" for every "not measured", for prices and for capability facts. It can never claim a measurement does not exist.

Design consequence: each ledger cell needs the upstream's edition date and the project's last successful check, and "not measured" should be computed from them, falling back to "not checked" when a source is older than the object's designation or a check failed.

## Design: Build and serve: a daily deterministic build that publishes immutable editions, and a service that reads the latest one

A scheduled job collects upstream responses into an append-only archive, normalises them into a rebuildable SQLite store, and builds one immutable data set a day, an "edition", as a pure function of a data state, a frozen method version and a schema version. The service (stack not chosen) reads only the current edition through a pointer file and owns only what must be live: wording that depends on today's date (observing windows, data-age notices) and any visitor state. Two append-only logs are the only irreplaceable data: what upstream said (archive) and what the project decided and published (record). Everything else is rebuilt from those and git. Measured on the two local pulls: a day's collection is about 25 requests and 21 MB, adding about 3 MB to the archive; the store for all 43,379 near-Earth objects is 53 MB and grew 0.5 MB in 3.4 days; a JPL-only edition is 1.7 MB gzipped and built in one second, with identical hashes across two separate runs. No live upstream call is permitted or needed: JPL's policy, read today, says "You may not embed these APIs in your website". The first step is to start the archive, because upstream keeps no history and each uncollected day is lost for good.

**Storage.** All under data/, outside git. (1) archive/journal.ndjson: one line per request attempt, successful or not (seq, source, scope, full request with every parameter written out, started_utc, http_status, headers, body_sha256, body_bytes, path, capture_check = ok | suspect | failed, trigger = primary | backstop | manual | import). archive/raw/<source>/<yyyy>/<mm>/<UTC time>-<sha12>.json.xz: the exact response bytes; 2.57 MB a day for JPL's two lists, 0.94 GB a year (measured). (2) record/record.ndjson: one hash-chained line per decision or publication, kinds batch, hold, release, mint, merge, withdraw, edition, issue, resolution. Accept and hold decisions and minted object keys are primary records, so a rebuild follows them and does not re-decide. (3) store/longshot.db, SQLite (proposed; standard library, needs the owner's yes), deleted and rebuilt at will. Tables: fetch (index of the journal); batch (batch_seq, source, as_of_utc, adapter_version, rows_sha256, state_hash); hold; object (the project's own key for all 43,379 near-Earth objects, first_designated, lifecycle, merged_into); alias (scheme, value, normalized, first_batch, closed_batch; one live owner per name); population and membership ("reachable" is a named population); source_row (each upstream record whole, by version: row_sha256 of the sorted-key form, row_json, first_batch, closed_batch); coverage (batch_seq, source, object_id, outcome = answered | unknown_to_source, source_edition_date; there is no error outcome); window_episode (first_seen_start, jpl_start, end_date, peak magnitudes, orbit_id, close_reason); claim (object, property, source, origin_ref, value_raw, value_num, bound, err_lo, err_hi, err_kind, qualifier, published, licence_class, embargo, first_batch, closed_batch; an index over source_row that is rebuilt when an adapter changes). The store holds no derived values; those exist only in editions. (4) editions/<edition_id>/manifest.json plus page/*.ndjson.gz and open/*.ndjson.gz, and editions/current.json as the pointer. In git: registry/sources.toml (per source: url, explicit params, change signal, expected version, cadence, stale_after_days, licence class, clock-driven fields, status), registry/properties.toml, registry/annotations.toml, method/<version>/ with a LOCK file of hashes, contract/schema-<n>.md and a conformance kit. The table definitions follow review-data.md section 4.3 with three changes: derived values are kept out of the store, the state hash covers rows as received and not parsed claims, and window_episode is added.

**Sync.** One command-line program with a verb per stage: collect (the only code that opens a connection; standard library only; its own environment), diff, ingest, build, publish, replay, digest. Daily, longshot-daily.timer at 10:00 UTC with Persistent=true so a run missed while the machine was off fires at boot (the hour is upstream-orbits.md's proposal, to be confirmed from the first week). Steps: (1) collect JPL's reachable list and near-Earth table whole: 2 requests, 18.4 MB; (2) diff against the last good captures and ingest; (3) JPL's single-object record for each reachable object that is new or has a new orbit solution: 7 to 10 requests typically, capped at 30, under 0.1 MB; (4) the Minor Planet Center identifier service for designations that appeared or vanished: 0 to 1; (5) ESA's change log as a private cross-check: 1 request, 2.25 MB; (6) change signals for slow sources (about ten HEAD requests, one SsODNet card, the arXiv listing): about 12; (7) ingest, build, publish; (8) ping a dead-man's check only after confirming today's captures are in the archive. Total about 25 requests and 21 MB a day; JPL sees 9 to 12, one at a time, two seconds apart. Weekly: the whole reachable list through the identifier service (73 requests), JPL's radar table, the digest. On a signal: a full SsODNet re-read (about 7,100 requests, two hours) on its own timer. Quarterly: replay from the off-machine copy and compare state hashes. Change detection: compare parsed rows with keys sorted, never bytes (0 of 7,229 reachable rows match as bytes, 7,007 once sorted); a new orbit solution number is the change key for the near-Earth table (all 342 changed rows have one), compared as a number after stripping the "JPL " prefix; fields the registry marks clock-driven are stored and kept out of every change list (192 of 222 changed reachable rows changed only in window fields); a window continues if its new start is not after the old end (192 re-dated, 24 closed on the two pulls). Failure handling: collect is idempotent per source and UTC day, and a second trigger elsewhere runs collect --only-if-missing; every write is temp file, sync, rename, then the journal line; ingest is one transaction per batch; a failed request writes a journal line and nothing else, with two more tries 30 minutes apart; a response of the wrong shape is archived as suspect; a format change fails a guard at ingest and becomes a source hold, the site keeps the last good data with its date, and after the adapter is fixed the held captures are ingested in order so history has no gap; a release check that fails leaves the pointer where it was. Holds never clear themselves. The follow-up list comes from diff on captures, so collection never waits on the store.

**Versioning.** Three stamps. Data state: a batch number plus a hash chained over every accepted batch, covering rows as upstream sent them, so a parser fix never changes a data state. Method version: a git tag and a directory method/<version>/ holding prior tables, thresholds, presets, row rules, the dated price scenario and the list of held-back references, with a LOCK file of hashes that a test checks; it changes only by hand at a gate, with a deposit. Schema version: the edition contract. An edition id is the three together plus a rebuild count, for example d000412.m0.1.s1.r1; before any method exists the method stamp is m0. The build applies the frozen method to the latest data state on every run and tunes nothing, so a new object gets its prior the day it appears and an object whose H moved (37 did in 3.4 days) gets the frozen table's row for its new H. Random seeds come from the object key, method version and property. Forecasts: a rule is frozen and deposited with a method release; an issue (what the site said about one object, with the hash of its inputs and the edition) is appended to the record when that object's inputs change; a resolution is appended by a person with three dates (observed, published, first seen here); a score is computed from those two, using the last issue whose data state precedes the earliest of the three dates, and is refused if the settling claim was among the inputs. Claims from held-back references are stored and dated but excluded from every derivation. To reproduce a shown number: the page gives the edition id; the record gives the hash of its manifest; the manifest gives the data state and hash, method tag and lock hash, code commit and lockfile hash; either read the kept edition (kept for good if a deposit, forecast freeze or correction refers to it, otherwise 30 days) or check out the commit, replay to that batch, build, and compare table hashes. Two prototype builds in separate processes gave identical hashes.

**Serving contract.** The service is given one directory per edition and one pointer, editions/current.json = {edition_id, manifest_sha256}. manifest.json names the schema version, data state and hash, method version and lock hash, code commit, the previous edition, per-source freshness (last successful check, the source's own edition date, stale_after_days, open hold), and each table's row count and sha256; it holds no build time. Tables are text, one JSON object per line with sorted keys and sorted rows, in two views: page/ (everything a page may show one cited value at a time) and open/ (only redistributable values and the project's own products). From the first edition: object, alias, population, population_member, property, state, source, claim, check (object, property, source, outcome = value | absent | not_checked, reason, both dates), window, change, field (one 77 kB payload for all reachable asteroids). With a method: row, ladder, elimination, observe_next, price, preset, mission_type, scenario, fact. With the record: forecast, forecast_issue, resolution, score. What the service physically opens is a packing of those tables, verified against the manifest and chosen with the stack: one read-only SQLite file per edition, or one document per object plus list payloads, or a load into the service's own database. I choose none. Publishing is: build under a temporary name, run release checks, append a record line, copy, replace the pointer last; rollback is the pointer written back. The service must take every scientific value from one edition and print its data date and method version; compute source age and window wording when a page is viewed; keep any visitor state in its own store keyed by object_id, forecast_id and edition_id; serve downloads from open/ only. It may select, sort, filter, count and compare stored dates with the clock. It may not call an upstream, derive or combine a probability, sum probabilities over a visitor's filter, write to an edition, or hand out page/ tables whole. One exception if visitors' predictions are ever scored: one published scoring function with test vectors. "Open now" is said only when the reachable list's last good pull is under two days old; of 212 windows open at the first pull, 24 had ended three days later. The stack choice depends on: whether visitors' predictions are stored and compared; whether history is queried on request or written into each edition; whether build and service share a machine; whether clock wording runs on the server or in the browser; and whether the owner will run and patch a process.

**First step.** Start the archive. Build collect, diff and the archive offline, prove them on the two pulls already on disk, and switch the daily timer on the day a JPL contact address exists. Done looks like: (1) data/archive/ holds the two existing pulls as four captures with journal lines, imported by copying, originals untouched; (2) longshot diff on them prints the measured numbers: reachable 7,229 to 7,231 with 2 added and 0 removed, near-Earth 43,367 to 43,379, 342 near-Earth rows changed, all with a new orbit solution and none in a physical field, 222 reachable rows changed of which 192 only in window fields and 23 with a new orbit, 16 then 17 reachable rows behind the table (the oracle script is in the report's appendix); (3) damaged responses (cut short, an HTML page, a 200 carrying an error, a count mismatch, an empty list) are archived and marked suspect, never good; (4) killing collect mid-write and rerunning leaves no partial file and one journal line per attempt; (5) a test proves only the collect package imports a network library; (6) with the address, the first live capture sends every parameter explicitly and adds spkid, soln_date and source to the near-Earth request, and full-prec after one comparison by hand; (7) seven consecutive UTC days each have a good capture of both lists, the dead-man's check was pinged each day, and archive/ and record/ have a copy off the machine. Items 1 to 5 need no decision and no network. It deliberately leaves out the store and its schema, object keys, claims, guards beyond a shape test, every other source, single-object calls, any model, any edition and any app. It shows nothing on a screen; its output is a daily series replacing one 3.4-day interval, which every tolerance and schedule in the design is waiting for. If the address takes more than a day or two, each day's pull can be made by hand through the same code path, as the two existing ones were; that is the owner's call.

### Weaknesses

- The site is at most as fresh as the last build. With a daily build and JPL's own day of lag on the reachable list, a change can take up to two days to appear.
- A correction waits for a build. An edition cannot be patched; a fix is an annotation, a build and a publish, which needs the build machine up, and this workstation is up 70% of the time.
- The boundary leaks in one place: if visitors' predictions are scored, the service must run one scoring function the build cannot run ahead of time.
- Determinism is a discipline agents will break (dictionary order, float formatting, a library upgrade that changes random draws). Tests catch it on the day, but a 2026 edition may not rebuild in 2031 if its locked packages no longer install, so editions that a deposit or forecast depends on must also be kept as files.
- An adapter fix rewrites the claim index for the past. Data states do not change and old editions rebuild at their own commit, but 'what did we believe on that date' is answered by the record and kept editions, not by today's store.
- A change of meaning upstream with no change of shape can pass the guards. Canary objects and a monthly hash of the documentation pages are thin protection.
- Four layers and seven verbs is a lot for one person. A script writing one JSON file would be a tenth of it. The extra is paid for by one requirement, forecasts frozen in advance and scored later; without the record, half of it could go.
- The build recomputes everything daily. That is one second for JPL's tables; the cost of the joint model for 7,231 objects is unknown, and if it is hours a cache is needed.
- Dates between deposits are self-attested. The record's hash chain and the off-machine lock are the only witnesses until a method release is deposited.
- If the build and the service run on two machines, something must carry editions between them, and I have designed only 'pointer last'.
- The evidence is thin: every rate rests on one 3.4-day interval plus ESA's log, the window rule has seen one full moon, and the run hour, follow-up cap and release tolerances are placeholders until a month of captures exists. No live JPL behaviour was tested, including the size of a full-precision response.
- The archive and the store hold responses that may not be redistributed, so both must stay private and the service must never expose the page view's files directly, whatever it is built with.

## Design: Fact log (journal first)

Keep the exact bytes of every upstream response, and keep an append-only journal of what each source said about each of its records and when, including every request that failed. Everything else is a view rebuilt from that journal: the per-asteroid ledger, "what changed", observing-window history, and the inputs of a frozen forecast. Records stay in the source's own shape, so the property schema, units, the three-state rule and the definition of "news" are views that can be corrected later and re-run over all history; only six journal line shapes must be right on day one. I built a 244-line standard-library toy today and ran the two pulls on disk through it: it reproduces the measured diff (7,229 to 7,231 reachable; 342 near-Earth rows changed, all with a new orbit solution; 222 reachable rows changed, 199 of them calendar-only; 1,388 to 1,389 under 7 km/s), gives the same running hash when built twice, rebuilds its index in 4.1 seconds, and writes no record at all under eight injected faults. The daily cost is about 22 requests (9 to 10 to JPL, one at a time), 21 MB down, about 3 MB of captures and 0.14 MB of journal kept. No live JPL call was made; the design chooses no app stack.

**Storage.** Files under data/ (outside git). captures/<source>/<yyyy>/<utc stamp>-<sha12>.body.xz and .meta.json: exact bytes plus request, times, status, headers, sha256; written once; a failed request writes meta only. journal/<nnnnnn>.ndjson: one segment per ingest run, written once; journal/chain.ndjson: per segment its sha256 and a running hash. Captures and journal are the only things that cannot be rebuilt (2.57 MB xz per JPL pull measured; journal 44.5 MB for the first load, then 142 kB a day).
Journal lines, six kinds on day one: fetch (fid, source, shape = hash of the full request, params, scope, started_at, transport, http_status, headers, body_sha256, capture path); verdict (fid, outcome accepted/held/released/rejected, guard results, api_version, upstream_edition, splitter_rev, by); asked (fid, source, key, outcome answered/unknown_to_source/failed, judged from the body); record (fid, source, key, kind new/changed/gone/rebase, hash of the sorted-key record, prev, body = the whole upstream record with strings left as received); mint (oid = the project's own object key, fid, source, key); alias (oid, scheme, value, norm, source, op add/close). Forecasts, resolutions, reviewed literature values and edition manifests are later written as record lines from sources named longshot.* or of kind reviewed.
index/longshot.db (SQLite from the standard library, proposed, deletable and rebuilt in seconds) holds the views: record_span(source, skey, hash, body, from_seg, to_seg); object(oid, minted_seg, lifecycle, merged_into) for all 43,379 near-Earth objects; alias(oid, scheme, value, norm, source, from_seg, to_seg); membership(population, oid, from_seg, to_seg); field_change(seg, source, oid, field, old_raw, new_raw, class clock/solution/tracking/elements/brightness/reach/push/physical/identity/format); change_event(seg, oid, kind, detail); window(oid, end_date, start_first_seen, mag_first, mag_last, last_listed_seg, state); claim(claim_key, oid, property, source, source_edition, origin_ref, value_raw, unit_raw, value_num, bound, err_lo, err_hi, err_kind, qualifier, upstream_date, published, embargoed, from_seg, to_seg, reader_rev); coverage(source, oid, last_answer_seg, last_answer_at, source_edition, last_try_at, last_try_outcome); source_status; derived(oid, quantity, method, inputs_hash, value, state, licence_class, first_seg); backlog(source, oid, reason) as a query.
In git: pipeline/collect.py (the one network module; writes captures only), pipeline/ingest.py (the only journal writer), index.py, readers/, registry/sources.toml and properties.toml, annotations.toml, method tags and a lock file. Also editions/<id>/ and freezes/<id>/ under data/.

**Sync.** Times UTC; where it runs is the owner's decision. collect, daily 10:00 (after JPL's trajectory run should have caught up with yesterday's Minor Planet Center circular; an assumption to confirm in week one): (1) JPL reachable list, 1 request, 2.6 MB; (2) JPL near-Earth table, 1 request, 15.8 MB as pulled so far; (3) ingest; (4) one JPL single-object call per reachable object that is new or has a new orbit solution: 7 to 8 a day on the measured sample, about 11 to 18 on busier days by ESA's log, capped at 60 with the rest left in the backlog view; (5) 0 or 1 Minor Planet Center identifier call for names that appeared or vanished; (6) about 11 probes of the slow sources (HEAD on static files, one SsODNet card for its build stamp, the arXiv listing); (7) ESA's change log as an internal cross-check if the owner agrees. Typical day: about 22 requests, 9 to 10 to JPL one at a time, about 21 MB down, about 3 MB of captures and 0.14 MB of journal kept; roughly 1.0 to 1.2 GB a year. collect --only-missing, daily 16:00 from a second place, writes captures only so the journal has one writer. weekly, Monday 11:00: the reachable list through the identifier service (73 requests), JPL's radar table (1), the digest. recrawl on a new upstream build; verify daily; drill quarterly from the off-machine copy.
Change detection: parse, sort keys, hash each record and compare per key (raw bytes cannot be compared; key order differs between pulls); a new orbit_id triggers follow-ups (all 342 changed rows had one); Last-Modified and ETag for static files; a changed request is a rebase that the change views skip; which fields count as news is a registry class, so the 199 calendar-only rows are journaled and kept out of the digest.
Failure: a timeout writes one fetch line and nothing else (three tries, 5/15/45 minutes apart, then wait for 16:00); a body that fails a guard is kept and held with no record lines, the site serves the last accepted data with its date, and a hold never clears itself; a format change holds every capture until the splitter or reader is fixed, then they are released in order, so the cost is delay and not a hole; after a reboot, captures and segments are whole or absent (temporary name then rename) and ingest journals any capture with no fetch line; a splitter bug is corrected by appending re-read lines, a reader bug by rebuilding the index.

**Versioning.** Three stamps on every derived value, edition and page: data (segment number plus the running hash, with each source's last accepted capture time), method (a git tag holding priors, thresholds, presets, the property registry, the source-precedence rule, the price scenario and the sealed-reference list; deposited at a gate), and code plus edition schema. "The data as of segment N" is a filter on from_seg and to_seg, not a copy. derive is a pure function of the views at a segment and a method tag (no network, no clock, seeds from object key and method version) and runs on every accepted segment, so a new asteroid gets its frozen prior the day it appears; tuning never runs unattended. A forecast is a journal record from longshot.forecast (question, object key, method, probabilities, inputs hash, input segment), written only when inputs change and never replaced; a resolution is a reviewed record with observed, published and first-seen dates; the score is a view over the two, and the scorer refuses if the forecast's inputs contain the resolving reference. Sealed labels are ingested and dated but marked embargoed and excluded until released. Each freeze also writes data/freezes/<id>/ with the exact input rows and a manifest (segment, running hash, method tag, code commit); the manifest's hashes are what is deposited outside. To reproduce a number: read the stamps (or the edition's record in the journal), check out that commit and method tag, index --upto the segment (which checks the running hash), derive, export, and compare table hashes with the edition manifest.

**Serving contract.** The app reads editions and nothing else, and never calls an upstream service. An edition is an immutable, self-describing data set identified by (segment, method, schema); publishing is an atomic swap and rollback is a swap back. Logical tables: objects, rows (state per object and property with the leading value, range, source, dates and per-source states), claims, derived, windows, changes, record (forecasts, outcomes, scores), field (one compact open-licence table for the picture of all asteroids), registries (properties, sources with licence class and stale-after age, presets, questions) and a manifest with the stamps and each source's dates. Two filtered forms: a page form that may show one restricted value at a time with its citation, and an open form with only redistributable values and the project's own products, which is the only thing downloadable or sent whole to a browser. The app may select, sort, filter, count, compare stored dates with the clock (the stale banner is computed at viewing time; "open now" only when the reachable list's capture is under two days old) and apply named conversions; it may not compute or combine probabilities. History (changes, windows, record, per-object history) is written into each edition by default; whether it is instead queried on request from a loaded copy of the index is left to the stack decision. Whether an edition is files or rows in a store, and what serves it, is not chosen. Visitor state, if any, lives in a separate store keyed by public ids and never enters the journal.

**First step.** Build the journal offline on the two pulls already on disk and prove it: collect with the network off (the two pulls imported as four captures), ingest for the two JPL lists with guards and the own-key identity step, and the index with record_span, object, alias, membership, field_change and window. Done means these pass as tests: (1) segments 1 and 2 reproduce the measured diff (7,229 then 7,231 reachable with 2 joined and none gone; 43,367 then 43,379; 342 near-Earth rows changed, all with a new solution; 222 reachable rows changed, 199 calendar-only and 23 with a new solution; 1,388 then 1,389 under 7 km/s; 17 reachable rows one solution behind); (2) building twice gives the same running hash and a deleted index rebuilds identically; (3) every single-fault case writes no record line and moves no cell to "looked for and absent"; (4) a run killed between any two writes resumes with no duplicate or gap; (5) data/ has one copy off this disk and a restore from it verifies. It deliberately leaves out readers and any property schema, SsODNet and every other source, priors, method and forecasts, the export and the app, the choice of where it runs, and any network call. The live switch-on is the day the owner supplies a JPL contact address. Estimated at one to two days of agent work; the toy that tested the idea took about an hour.

## Design: One box

One command (`longshot daily`) on one timer on one machine asks JPL for its two bulk lists (2 requests, 18.4 MB down, 2.6 MB kept), writes each response to disk unchanged, appends a line per request to a journal, and replays the journal into one SQLite file. Only the raw responses and the journal (every request, failures included) are kept forever; the database, every derived number and the data set the app reads are build products that can be deleted and remade, so there are no migrations and no database backups. That means very little must be right before collecting starts: what JPL is asked for, that raw bytes are kept even when rejected, and that every attempt leaves a journal line. Table shapes, the claim record and the object key can be changed later by replay. I ran the core today as a 200-line standard-library script on the two pulls on disk: it reproduced the measured diff exactly (7,229 to 7,231; 342 new orbit ids; 222 reachable rows changed, 199 of them only in window and radar-opportunity fields; 17 rows on an older orbit), took about 1 s per pull, made a 66 MB file growing 0.2 MB a day, rebuilt identically, survived SIGKILL before commit, and across 15 damaged-response cases never turned a cell into "looked for and absent". One case (rotation periods times 60) got through, which showed a guard the list needs. Nothing chooses the app's stack; SQLite for the pipeline's store needs the owner's yes.

**Storage.** KEPT FOREVER (outside git, append-only, mirrored): `data/raw/<source>/<year>/<utc>_r<run>_<sha12>.json.xz` (every response body as received, xz, read-only after write; stored by date because JPL shuffles key order so no two responses are byte-equal); `data/log/journal-<year>.ndjson` with four line types: request (run, node, at UTC, source, method, url, every parameter, status, headers, bytes, sha256, path, outcome ok|http_error|timeout|refused), verdict (accepted|held with guard report and adapter version), release (owner releases a hold), export (code commit, method, schema, hash of the published data set); later `data/log/forecast-<year>.ndjson`. In git: code, `registry/sources.toml` (id, kind catalog|service|table, URL and every parameter, cadence, change signal content|head|body-field, expected version string, min gap, stale-after age, licence class, citation), `registry/fields.toml` (per field: class id|orbit|value|clock, later its property), method files, annotations, resolutions.

BUILT, DISPOSABLE: `data/longshot.db` (SQLite), six tables in the first step, all run today:
- run(run PK, started_at, code [git commit], chain [sha256 of previous chain plus the body hashes of responses accepted in this run])
- fetch(fetch_id, run, node, source, method, request, request_sha, scope ['*' or object], at, http_status, headers, body_sha256, body_bytes, raw_path, api_version, upstream_date, outcome, verdict, report)
- object(key PK [10 base-32 chars hashed from the first designation ever seen, so a rebuild mints the same key], first_des, first_run, kind, merged_into); all 43,379 near-Earth objects keyed
- alias(scheme [des|number|name|spkid|ssodnet], value, key, source, first_run, closed_run; unique on live scheme+value)
- source_row(source, key, first_run, closed_run, sha [of sorted-key JSON], changed [JSON list of fields that differ from the previous version], row_json [every field as received]; PK source,key,first_run)
- coverage(run, source, key ['*' = whole list read and passed guards], outcome returned|unknown_to_source), written only inside the transaction that ingests an accepted response
Week two adds claim(claim_id, key, property, source, value_raw, unit_raw, value_num, value_text, bound, err_lo, err_hi, err_kind, qualifier, origin_ref, published, upstream_date, first_run, closed_run), filled from source_row by adapters, no one-value-per-cell constraint.
Folded away: batch (run + fetch.verdict), membership (the live jpl.nhats rows), derived tables (the export, remade by replay), content-addressing, a hash over canonical rows.
Also built: `data/export/<run>-m<method>-s<schema>/` with `export/current`, `data/status.json`, `data/digest/<year>-W<week>.md`.
Measured size: 65.8 MB after the first pull, +0.70 MB per 3.4 days (about 75 MB a year; allow 110), +54.5 MB on a day every row changes. Raw: 0.94 GB a year.

**Sync.** One systemd timer and one oneshot service holding a file lock: `longshot-daily.timer` with `OnCalendar=*-*-* 10,22:00:00 UTC`, `Persistent=true` (catch-up after power-off). 10:00 UT is the pull; 22:00 UT is the retry and makes a request only for a source with no accepted pull for that UTC date, so a good day is 2 JPL requests, not 4.

Stages in order, each repeatable, a later one cannot undo an earlier one: (0) catch up any journal run the database lacks; (1) collect: near-Earth table then reachable list, sequential, 5 s apart, every parameter explicit (`dv=12, dur=450, stay=8, launch=2020-2045`; the table with `spkid`, `soln_date`, `source`, `full-prec` added), one retry after 60 s, stop on 429/503; raw file renamed into place before its journal line is written; (2) mirror new raw files and the journal to one mirror path, never deleting; (3) guards, verdict line, ingest in one transaction; (4) derive and (5) export, empty in the first step; (6) write status.json, Monday digest, signal the alert URL.

Size per day: 2 requests to JPL, 18.4 MB down, 2.57 MB kept (xz, about 4 s CPU), about 1 s to ingest; about 100 near-Earth rows and 66 reachable rows differ, about 7 reachable rows outside window fields, under one new reachable object, about 170 new row versions and 0.2 MB of database. From week one an edition watch adds about 10 requests (HEAD on SsODNet's, LCDB's, Pravec's, MITHNEOS's and ALCDEF's static files plus one SsODNet record); a changed date raises a status line and does not start a crawl. First live day is 3 JPL requests (table in old and new form) to measure what the new request changes.

Change detection: JPL has no ETag, Last-Modified, body date or changed-since filter, so both lists are pulled whole; each row is resolved to our key, written as sorted-key JSON and hashed; a new version is stored only when the hash differs, with the list of changed fields. `fields.toml` classes decide what is news: clock fields (window and radar-opportunity) never; orbit fields once per object as "new orbit solution" keyed on orbit_id; value fields are the change list; added fields are "request changed".

Guards before ingest: body parses with signature/data/count and no error key; version string matches; count equals rows; required fields present; no duplicate designation; row count within tolerance; filled count of each physical field has not fallen; no more than 20 rows changed a physical field and no more than 1% changed while keeping their orbit_id; no more than 10% of rows changed; every reachable designation resolves in the table. Tolerances are placeholders until a month of pulls exists.

Failure: no answer leaves a journal line and nothing else, and the 22:00 firing retries. A guard failure archives the raw file, writes a held verdict, leaves the last accepted data live and sends a failure signal. A permanent format change holds every day while archiving every day; after the adapter is fixed, `longshot release` ingests the held pulls oldest first, each as a new run. Nothing is ever inserted into the past. A dark machine is caught by the dead-man's switch after 36 h. A kill or reboot mid-run rolls back and the next firing catches up (tested today).

**Versioning.** Three stamps, never one "release": data state (run number N plus `chain(N)`, a hash chain over the raw response hashes accepted so far, which does not change when a parser does and can be checked by anyone holding the raw files); method version (a git tag holding prior tables, thresholds, presets, price scenario, registries and code, changed only by hand at a gate); schema version (the shape of what the app reads). Every data set and page carries `data N (date) · method X`.

Current data and frozen science coexist because row versions are never rewritten: "the data as of run N" is a query (`first_run <= N and (closed_run is null or closed_run > N)`; 1 to 15 ms today). Applying a frozen method is a pure function of that state and the method's files (no network, no clock, seeds from object key and method version) and runs every day, so new objects get priors from the frozen table; tuning a model never runs unattended.

Predictions are stored when made: each run appends to `data/log/forecast-<year>.ndjson` a line per question and object whenever the registered method's prediction changes (probabilities per outcome, method tag, run, chain, inputs hash). A freeze is one committed file naming the questions, rule text, method tag, chain(N) and the forecast log's hash; that file is what gets deposited, and it commits to the data state without publishing restricted values. Resolutions are hand-confirmed lines in git with three dates (observed, published, first seen here). A score is a function of those two files: the scorer takes the last forecast line whose run predates the earliest of the three dates and refuses if there is none.

To reproduce a shown number later: the page gives run and method; the journal's export line for that run gives the code commit and the hash of the published data set; check out the commit, `longshot rebuild --through N` into a scratch file, export with that method, compare hashes. A parser fix found later changes the rebuilt past, and the difference from the recorded hash is itself the correction record. None of this is built in the first step; the first step supplies as-of state and the chain.

**Serving contract.** The app, whatever it is written in, reads exactly one thing: the current export. It never opens longshot.db, raw files or the network, never writes to the export, and computes no scientific value.

An export is immutable and named by its stamps (`<run>-m<method>-s<schema>`). Publishing is one rename of `export/current`; rollback is one rename; on another machine it is one directory copy then the rename there.

`manifest.json`: schema, method, run, chain, build time, content hash, and per source its edition date, last successful check, last change, stale-after age and licence class.

Tables by meaning: object (key, display name, every alias for redirects, populations); row (one per object and property: state measured|limit|prior|not_checked, value as text and as bounds with unit, lead source, original reference, edition date, checked date, reason when not checked); claim (every statement shown, after the licence filter); reach and window (with the orbit solution the figures were computed on and an as-of date); elimination, price, observe_next (per preset or scenario); field (one compact payload of redistributable columns for the all-asteroids view); change (dated events, window fields excluded); record (forecasts, resolutions, scores); the registries. Two licence views from one filter: a page view (single cited values) and an open view (redistributable values and our own products); any download comes from the open view.

The app may select, sort, filter, count, compare manifest dates with the clock for a freshness banner, and apply unit conversions the registry names. It may not compute or combine a probability or range, sum probabilities over a filter, or say "open now" from a table more than two days old. Staleness is computed at viewing time so it is true when every job is dead. Visitor state, if any, lives in a separate store keyed on object keys, question ids and run numbers; the pipeline never reads it.

Left open for the stack conversation: the physical form (the same tables as one read-only SQLite file or as JSON files) and whether history views are queries on request or tables written ahead. Those turn on whether the server can open a local file, whether pages are made on request, whether the app runs on this box, and whether visitors write anything.

**First step.** Build `longshot daily` as far as archive and replay, prove it offline on the two pulls already on disk, and start its timer the day the JPL contact address exists. It is the six tables, `net.py` (the one module that opens a connection), `collect.py`, `guards.py`, the two JPL adapters, `ingest.py`, `status` and `diff`, with no package beyond the standard library (SQLite pending the owner's yes). About one to two days of agent work by my estimate; the 200-line prototype in the report's appendix is its core and already passes most of this.

Done means: (1) `longshot replay data/snapshots` adopts the two pulls as runs 1 and 2 and `longshot diff 1 2` prints the measured figures (reachable 7,229 to 7,231 with 2026 VQ5 and 2026 WV1 joined and none left; near-Earth 43,367 to 43,379; 342 rows with a new orbit_id; 222 reachable rows changed, 171 only in window start or brightness, 199 only in window and radar-opportunity fields, 23 with a new orbit; 17 rows on an older orbit), committed with the four file hashes as the golden test. (2) The mutation suite passes: the 15 damaged-response cases, with the times-60 case now held, each asserting no cell becomes "looked for and absent". (3) Deleting the database and rebuilding gives identical tables; killing the job mid-run and rerunning gives the same file. (4) A test fails if any module but `net.py` imports a network library. (5) The timer is installed but disabled; on the day the address exists it is enabled and the first live day makes three JPL requests (near-Earth table in old form and in new form with `spkid`, `soln_date`, `source`, `full-prec`, then the reachable list) so the effect of the new request is measured before history accumulates. (6) `status.json` shows two accepted pulls for the day, the mirror copy verified, and the alert service has heard from it.

Deliberately left out: claims and properties, any source but JPL's two lists, priors, the export, the app, per-object calls, the edition watch, the digest, forecasts. The reason this comes first: each uncollected day is gone (a 3.4-day gap already hid at least 82 orbit solutions), and everything else can be redone by replay.

### Weaknesses

- One machine is one point of failure for history. On the workstation's last six weeks about one day in eight would have been a hole (a colleague's measurement). A hole thins the history without corrupting it, but can never be filled.
- Correctness rests on replay staying deterministic and affordable: every adapter must read every past response form forever, and rebuild time grows about six minutes per year of daily pulls (extrapolated from two pulls).
- Whole rows as JSON are simple and wasteful: a day every row changes costs 54.5 MB, and a field-history question parses JSON. Tested to about 100,000 versions, not millions.
- The key is derived from the first designation seen. If an early alias decision is corrected, which of two merged keys survives could change on rebuild; once anything public or frozen points at keys, merges need a pinned file in git.
- Holds need a person. With the owner away, a format change means days archived but not ingested and a site that says it is stale.
- Guard tolerances are placeholders from one 3.4-day interval; expect false holds in the first month. My prototype let a unit change (periods times 60) through until I specified another guard, so the list is not proven complete.
- Leaving out per-object JPL calls loses covariance and force-law history that cannot be fetched later, and full precision of the fitted push values if `full-prec` does not reach them. This is the omission most worth overruling.
- It does nothing to make physical data faster: sizes, spins and classes stay dated, and the watch only reports a new edition.
- The journal is a home-made convention; a write-order bug could orphan a file. File names carrying time, run and hash, plus a verify command, are the only net.
- One-UTC-day granularity: a catch-up pull at boot can land at any hour, so the lag between JPL's two lists varies between runs.
- SQLite takes one writer. That suits one job and rules out visitor state in the same file.
- Nothing was run against a live service: the request additions, the response size at full precision, the 10:00 UT timing and systemd's catch-up on this machine are untested. The claim table, service and table sources, the export and the forecast log are designed, not run.

### Why the first step could be wrong

- It collects the data that bears least on the project's question. The daily churn is orbits, tracking and observing windows; no physical field changed in 3.4 days, and the finding that changed the site's content today (35 rotation periods in a table the project did not use) came from adding a source, not from keeping history. If the prototype is what matters most, the fixture slice teaches more per day. Cheaper test: mark which values in the DESIGN.md section 3 entry are read from a past date. Today that is 'what changed this week', the first start of an observing window, and the inputs of a forecast. If the list stays that short, the archive is insurance and should cost about a day.
- The loss it prevents is small for now. Nothing is frozen or scored before the public launch, a freeze can carry its own inputs, and H changed for 4 reachable objects and delta-v for 7 in 3.4 days, so a weekly pull would have served scoring. A gap before the first freeze costs intermediate orbit solutions and window rewrites. Cheaper alternative: two requests by hand each day, as the two existing pulls were made, give the same insurance with no code. If the step is not finished in three days, do that and stop building.
- Its offline test proves little that is new. Eight agents and I have now diffed the same two files and got the same answer. Everything unknown is live: the size of a full-precision response, whether full precision reaches the fitted push values, whether JPL's id changes at numbering, when the reachable list catches up, and what the timer does at boot. If the contact address stalls, the step delivers a disabled timer. Cheaper test: one supervised pull with the new fields on the day the address exists, before the collector is finished. It takes three requests and about ten minutes.
- It could be proven on the wrong machine. All three designs take 10:00 UT from upstream-orbits; that is 03:00 on this workstation, which was often off at that hour. On the other days the pull lands at boot or at the 15:00 local retry, a few hours after the Minor Planet Center's circular, when the reachable list was measured still on the previous day's orbits. No experiment is needed, because the machine's uptime already answers it. The owner picks the machine first.
- The journal line is the one format kept for good, and it would be fixed after seeing only the two easiest sources, each a whole list in one request. A service asked one object at a time (SsODNet, about 7,100 requests a crawl) or a static file with a modification date may not fit it. Cheaper test: before the first live day, write journal lines for the 1,704 SsODNet records already in the research archive and for one HEAD response, and put a format version on every line.
- JPL could read a daily 16 MB pull in which 99% of rows are unchanged as redundant. Its policy says 'Automated processes must not make unnecessarily frequent, repetitive, or redundant requests' (https://ssd-api.jpl.nasa.gov/doc/, read today). JPL offers no filter by change date, so there is no lighter compliant route, and one request a day per list is modest, but the judgement is JPL's. The contact address is what lets JPL say so instead of blocking. Fallback: the reachable list daily, and the table less often or with fewer fields.
- Treated as a gate, it delays the two things the owner has asked for. All three designs hold the stack conversation on day 14 with a data set in hand, yet none of the questions that choice turns on is answered by two weeks of pulls: whether visitors' predictions are stored, whether history is queried on request, whether the job and the app share a machine, whether he will run a process. Cheaper test: ask him now. If an answer changes what the collector must write, the step was ordered wrongly; I expect none does.

Compared with UTC capture times it is 7 or 8 hours off and ambiguous for one hour each November. fact-log notes the zone in its source list only.
- build-and-serve's first step is inconsistent with its own timetable. Its done list needs seven consecutive UTC days and a mirrored record/ folder, but the timetable gives the step days 1 to 2 and creates the record file in days 2 to 5.
- Checked today and found correct: the JPL policy quotes in all three designs (https://ssd-api.jpl.nasa.gov/doc/); the fields spkid, soln_date, source and full-prec (https://ssd-api.jpl.nasa.gov/doc/sbdb_query.html); the reachable-list defaults dv 12, dur 450, stay 8, launch 2020-2045 and the 2019 change of launch range (https://ssd-api.jpl.nasa.gov/doc/nhats.html). ## Judge 2

Winner: one-box

- one-box: maintainability 9, freshness and honesty 7, extensibility 7, fit 8. Risk: History rests on one machine and one mirror path. If that machine is the workstation, about one day in eight is a permanent hole (five dark days in 41, per review-ops), and its 10:00 UTC run is 03:00 local, an hour at which the machine was on 23 of 42 nights. Object keys are recomputed from designations on every rebuild and never recorded, so a corrected alias rule can change a key that a page or a frozen forecast already cites. Per-object JPL calls are left out, which loses each superseded orbit's covariance and force law for good. Guard 8 as written would hold the reachable list every day. It also assumes a Linux box with a systemd timer before the owner has said where the job runs. Why it still wins: only raw responses and a request journal are permanent, everything else is rebuilt, the document prices every omission, and it reported its own failed test. Its prototype reran here with the stated output.
- fact-log: maintainability 5, freshness and honesty 8, extensibility 9, fit 5. Risk: It makes a parsed log the permanent record. Six line shapes, each source's key and every identity decision must be right on day one. A mistake is never removed, only corrected by more lines that every view must then understand. Capture time and journal order diverge whenever a held pull is released late, and the scoring rule is not shown to be safe when that happens. Restricted-licence records sit inside hash-chained segments, so honouring a takedown breaks the chain. It has the largest first step (800 to 1,200 lines by its own estimate), with identity and crash safety untested and nothing visible for two weeks. Its strengths are the richest history and the best reasons for 'not checked'. Its toy reran here with the stated output.
- build-and-serve: maintainability 7, freshness and honesty 8, extensibility 8, fit 7. Risk: The most machinery for one person: two logs, a store, editions with retention rules, a pointer, seven verbs, a contract and a test kit, all before any science. Rebuilds prove something only while builds stay byte-identical, which is a discipline to keep for years. The cost of a daily full rebuild once the joint model exists is unknown, and moving editions from a build machine to a serving machine is not designed. Its sizing prototype was not kept and had no guards or claims, so its store and edition sizes cannot be rerun; its diff oracle did rerun here correctly. It is right on three points the winner should take: decisions (keys, holds, what was published) are recorded and not re-derived, published editions that something cites are kept as files, and its first step is the smallest.

**Recommended first step.** Start the archive. Build one standard-library module that makes a request, writes the response bytes to disk unchanged, and appends one journal line per attempt, failures included, with every request parameter written out. Add a `diff` that compares two stored pulls after parsing. Prove both offline on the two pulls already on disk, then switch the daily job on the day the JPL contact address exists.

Done looks like:
1. The two pulls are imported as four captures with journal lines. The first one's time is marked as inferred and the originals are untouched.
2. `diff` prints the measured figures with the definitions pinned. Reachable list 7,229 to 7,231, with 2026 VQ5 and 2026 WV1 joined and none left. Near-Earth table 43,367 to 43,379. 342 near-Earth rows changed, all with a new orbit id and none in a physical field. 222 reachable rows changed: 171 only in window start or brightness, 192 only in the four window fields, 199 only in the eight calendar-driven fields, and 23 with a new orbit id. 16 then 17 reachable rows are one orbit behind the table. I recounted all of these today.
3. A truncated body, an HTML page, a 200 that carries an error, a count mismatch, an empty list and an emptied column are each archived and never marked good. A kill mid-write leaves no partial file and exactly one journal line per attempt.
4. A test fails if anything but the collector imports a network library, and the third-party package list is empty.
5. On switch-on day the near-Earth request adds spkid, soln_date, source and full-prec, and one extra old-form pull is made that day to measure what the new form changes.
6. Seven consecutive UTC days each have a good capture of both lists, a dead-man's signal went out each day, and a copy off this disk verifies by hash.

What it proves: unattended daily capture works within JPL's terms on the chosen machine. It replaces one 3.4-day sample with real daily change rates, the hour at which JPL's two lists agree, and what full precision adds. It shows that calendar churn separates cleanly from news.

What it leaves out: the database and its schema, object keys, the three ledger states, content guards with holds, every other source, per-object calls (unless the owner says in), any model, the export, the app and the stack.

The designs estimate one to two agent-days. Items 1 to 4 need no decision and no network.

### Why the first step could be wrong

- It spends the first days on the data that matters least to the project's question. No physical field changed in 3.4 days, and today's largest finding (35 rotation periods in Pravec's table, 7 of them under 6 km/s) came from adding a source, not from keeping history. If a visible prototype is the priority, the fixture slice or that table is a better first two days. The step is small enough to run alongside.
- The urgency is overstated in all three designs. No forecast is frozen yet, so history before the first freeze is not needed for scoring. A missed day loses about 100 superseded orbit solutions and that day's window dates. The step is justified because it is cheap, independent of the stack and the source of every tolerance, not because of loss alone.
- The owner's stack opinions have not been asked. If they settle where scheduled work runs, or what 'not static' means to him, the job's home changes. The raw files and journal survive any answer, but an hour's conversation first could save a move.
- 10:00 UTC may be the wrong hour. The only measurement is that JPL's reachable list was still behind its orbit table 12.7 hours after the Minor Planet Center's circular. JPL's page says 'daily analysis' and gives no time of day (https://cneos.jpl.nasa.gov/nhats/intro.html, read today). On the workstation 10:00 UTC is 03:00 local, so about half the pulls would run at boot instead, after that day's circular.
- The new request form is untested. The size at full precision is unknown, and JPL's page does not say whether full-prec reaches the fitted push values (https://ssd-api.jpl.nasa.gov/doc/sbdb_query.html, read today). If it does not, the per-object calls this step leaves out become necessary, and what they would have captured in the meantime is gone.
- With no database, 'good' is judged by shape and a diff report, and nothing can be held. A subtly wrong response would be archived and counted as good for a few days. Nothing is lost, but the alert is weaker than one-box's guards.
- JPL's policy says automated processes 'must not make unnecessarily frequent, repetitive, or redundant requests' and should reuse 'unchanged or predictably changing data' (https://ssd-api.jpl.nasa.gov/doc/index.php, read today). Two full pulls a day of a table in which under 1% of rows change is a reading of 'reasonably necessary' that review-ops and I share. Nobody has asked JPL, and the project's rule bars asking yet.
- Every acceptance number comes from one interval that straddled a full moon. Daily diffs will look different, with roughly 200 window-start rewrites a day. The golden test proves the code against two files, not against normal days.
- The exact request behind the two pulls on disk was not recorded beside them. Importing them means reconstructing it from the 53-field list and the research scripts. If the reconstruction is wrong, the old-form comparison on day one is off.
- If the chosen machine is the workstation and there is no second trigger, the step will record about one missing day in eight and cannot fill them.

### Decisions the owner must make first

- The JPL contact address and product name. JPL requires a 'valid, application-specific User-Agent request header that includes correct product name, version, and contact information' from automated clients (https://ssd-api.jpl.nasa.gov/doc/index.php, read today). A role address that forwards to an inbox he reads is enough. It blocks switch-on only; coding and offline tests need nothing. Related: may one pull a day be made by hand through the same code until the address exists?
- Which machine runs the daily job, and where its alerts go. It needs to be on every day, with a stable outbound address, about 1 GB of disk a year and one JPL request at a time. The workstation was powered 70% of the last 41 days. Also decide whether a second, capture-only trigger runs somewhere else from the start. This is about the collector only and does not choose the app's host.
- Where the off-disk copy lives: a private git remote, and a place for data/ (raw files and journal), ideally with delete and overwrite forbidden. I confirmed today that the repository has no remote; review-ops found no backup.
- Yes or no to daily pulls in place of the plan's weekly refresh, and to a collector with an empty third-party package list (AGENTS.md asks for a yes on the package list).
- Yes or no to adding spkid, soln_date, source and full-prec to the near-Earth request from the first live pull, and to three JPL requests instead of two on that one day.
- Per-object JPL calls, in or out from the start: one single-object call for each reachable object with a new orbit, 7 to 10 a day. Out loses each superseded orbit's covariance and force law permanently. In adds a second request shape to the first step. It is the only omission in the step that cannot be made good later, so it should not wait for day 14.
- Not needed to start, but needed for the step after: SQLite as the pipeline's working store; the project's own recorded object key for all 43,379 near-Earth objects; what 'not static' means to him (data that refreshes itself, pages made on request, or holding no upstream copy, which JPL's terms rule out); and whether visitors make predictions.

### Errors found

- The brief's measured figures say 221 reachable objects changed. My recount of the two snapshots gives 222, as all three designs and the reports say (review-extend notes an earlier count of 221).
- upstream-orbits section 3 says 204 of the 216 changed window starts are one edit, 21 November to 27 November. 187 rows made that move. 204 is 216 minus the 12 windows that vanished; the other 17 are four that started on 22 or 23 November and 13 that moved to a different later date.
- 'Real' changes on the reachable list are stated three ways: 51 (upstream-orbits and review-ops, ignoring window start and brightness), 30 (review-extend, ignoring the four window fields) and 23 (one-box and fact-log, ignoring all eight calendar-driven fields). Each is arithmetically right. Only 23 has a meaning: every change outside those eight fields sits on a row with a new orbit solution. The three designs' golden tests expect three different sets, and upstream-orbits' proposed test ('222, of which 51 are real') contradicts the field classes all three adopt. Pin 171 / 192 / 199 / 23.
- review-extend says JPL's two lists disagree on H by more than 0.05 for 327 objects. That is a floating-point artefact. 326 of them differ by exactly 0.05, because the list rounds a two-decimal H to one decimal. In decimal arithmetic one object differs by more: 2026 VQ19, 25.29 against 25.4, on a row computed from an older orbit. review-data's 'agrees to rounding, 1 exception' is correct.
- one-box guard 8 ('no more than 1% of rows changed while keeping their orbit_id') has no scope. On the reachable list 199 of 7,229 rows (2.75%) did exactly that between the two pulls, all in calendar-driven fields. As written it would have held run 2 and would hold every daily pull. The prototype does not code guards 8 or 9, so its done-criterion 'the times-60 case now held' is not yet demonstrated.
- one-box guards 8 and 9 contradict its own handling of a changed request. On the day spkid, soln_date, source and full-prec are added, every row changes with the same orbit id, so both guards would hold a pull the design says is accepted. The prototype accepts the 'new field' case only because those guards are not coded.
- All three designs get their per-day figures by dividing the 3.36-day totals by 3.36: one-box has 66 reachable rows and about 170 row versions a day, fact-log 172 record lines and 142 kB a day, build-and-serve 55 MB a year of store growth. The interval held one full-moon jump. JPL stamps each open window with the day it ran (212 windows carried the pull date on 21 November), so daily pulls should show roughly 200 calendar-only row changes a day on the reachable list, about three times the stated figure. Sizes stay trivial; a tolerance or digest built on '66 a day' would be wrong.
- one-box presents its key as the 'own object key' the reviews ask for. It is a hash of the first designation seen, recomputed on each rebuild and recorded nowhere. review-data specifies a key 'never derived from any upstream id', and review-extend one 'never built from a designation'. The design admits the consequence in weakness 4 but lists it for the owner as the same decision.
- upstream-orbits gives 'lagging reachable rows: 16 or 17 is normal' as a monitoring baseline. Those counts were taken 4.1 and 12.7 hours after a circular. At the proposed 10:00 UTC run, about 21.5 hours after, the normal value is unknown and may be near 2. Also, six objects were behind at both pulls, not two; two (2019 YS3, 2026 DM15) sat on the same stale pair and four had been refitted again.
- fact-log section 4.2 sizes each follow-up call at '2 to 7 kB', citing upstream-orbits. That report gives 2.2 to 6.5 kB for 14 saved responses whose request options were not recorded, and lists the size with covariance as not checked.
- All three designs put the main pull at 10:00 UTC, and none notes that this is 03:00 on the owner's workstation (UTC-7, checked today). review-ops found the machine on at that hour on 23 of 42 days, so there the stated reason for the hour (before the day's circular) would fail on about half of days. one-box mentions boot-time catch-up only in general.
- Some evidence is overstated. one-box's 'no cell became absent across 15 cases' was checked on 18 probe cells (6 objects by 3 fields) of the near-Earth table. build-and-serve's sizing script was not kept. fact-log's toy has no identity step and was not killed mid-run (self-declared).
